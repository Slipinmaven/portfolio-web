# Frontend instructions

These instructions extend the repository-root `AGENTS.md`. Also follow
`web/AGENTS.md`, which is generated by Next.js and contains framework-specific
guidance. Do not edit that generated file.

## Architecture and file ownership

- This app uses Next.js App Router, React, TypeScript, and Tailwind CSS.
  `src/app/` owns URL structure, route entry points, layouts, and framework
  metadata. Keep route files thin; put feature behavior and UI in
  `src/features/<feature>/`.
- Existing route groups separate the public portfolio, dashboard, and
  authentication routes. Existing features include `auth`, `admin`, and
  `portfolio`. Add a domain feature when implementing it; do not create empty
  folders for roadmap items.
- Keep feature-specific API calls, state, types, and components with their
  owning feature. Introduce shared UI or shared API transport only when
  multiple features have a real common need; avoid duplicating request/error
  handling as the frontend API surface grows.
- Keep `admin` responsible for the admin/editor workspace shell, navigation,
  session guard, and workspace-specific UI, not for every content domain.
  Admins and editors share this workspace; follow backend policy for role
  permissions instead of inferring them from the feature name. Keep public
  project, post, page, or other domain behavior with the corresponding feature.
- Use Server Components by default. Add `"use client"` only at the smallest
  boundary that needs browser state, event handlers, or browser APIs.
- Follow existing TypeScript, import-alias, component, Tailwind token, and CSS
  Module conventions. Preserve the existing light/dark system and design
  tokens; do not add arbitrary styling conventions or a UI framework without a
  concrete need.

## User experience and security

- Treat accessibility and responsive behavior as part of implementation:
  semantic structure, keyboard support, visible focus, labels, appropriate
  contrast, and clear loading, empty, success, and error states.
- Keep access tokens in memory, never in `localStorage` or `sessionStorage`.
  The backend owns refresh credentials in HttpOnly cookies and is the
  authorization boundary. Frontend route guards improve navigation and UX;
  they do not secure backend operations.
- Use the existing auth/session helpers rather than creating a second token
  store. For protected feature requests, use a consistent shared request path
  when one is established; do not independently invent token-refresh behavior
  in each feature.
- Keep secrets and server-only configuration out of `NEXT_PUBLIC_*` variables.
  Use the configured API base URL and existing credential/CORS conventions.
- Validate user input for usability, but rely on backend validation and
  authorization for enforcement.

## Validation and documentation

- The current package scripts include `npm run lint` and `npm run build`.
  There is no frontend test script yet; do not claim tests ran unless a test
  runner has been added and used.
- For substantial new interactive behavior, decide on focused automated tests
  rather than treating lint or build as behavioral tests. Add test tooling only
  when the change warrants it, and cover important success and failure states.
- Run the narrowest applicable checks, then build when changes affect
  application code, routing, types, or configuration.
- Update `web/README.md` when frontend architecture or setup guidance changes.
